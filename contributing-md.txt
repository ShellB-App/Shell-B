# Contributing to Shell:B

First off: thank you. Every contribution — a bug fix, a documentation tweak, a new voice model, a cleaner Docker compose file — makes this project better for everyone who runs it on their own hardware.

Shell:B is built on one principle: **your AI assistant belongs to you, not to a corporation.** Everything here is AGPL-3.0 licensed so that no company can take our work, wrap it in a SaaS, and sell it back to us without giving anything back. That's non-negotiable.

If you're cool with that, read on.

---

## What kind of contributions are welcome?

- **Bug fixes** — if something breaks your deployment, we want to know
- **Documentation improvements** — networking guides, hardware recommendations, setup troubleshooting
- **New voice models** (Kokoro, Piper, etc.) — add them to the assets library
- **Image generation workflows** — new ComfyUI JSON pipelines, custom nodes
- **Docker / deployment improvements** — better compose files, resource optimization for lower-end hardware
- **Dashboard UI enhancements** — React components, theme tweaks, accessibility fixes
- **Translations** — i18n files for the web interface

## What about corporate contributions?

We welcome individual contributors from anywhere. If you're contributing on behalf of a company:

1. You must have explicit permission to contribute under AGPL-3.0
2. You must confirm your contribution won't be used in any proprietary product
3. We reserve the right to reject any contribution that appears to be part of an attempt to extract value from this project without contributing back

**TL;DR:** Individuals, students, hobbyists, researchers — absolutely welcome. Companies trying to use contributions as a backdoor into proprietary products — we'll spot it and say no.

## How to contribute

### 1. Fork and clone

```bash
git clone https://github.com/EveAeternam/Shell-B.git
cd Shell-B
```

### 2. Set up your environment

See the [README](https://github.com/EveAeternam/Shell-B#readme) for full setup instructions. At minimum:

- Docker & Docker Compose
- Python 3.12+ (or use the provided container)
- Ollama for local LLM inference
- Git

### 3. Create a branch

```bash
git checkout -b feature/your-feature-name
# or
git checkout -b fix/what-you-fixed
```

### 4. Make your changes

- **Code:** follow existing style. If there's no linter, at least be consistent with what's already here.
- **Docs:** write for humans, not machines. Clear > clever.
- **Assets:** include license, author, and source URL in your additions
- **Docker:** test your changes — we don't accept compose files that don't actually work

### 5. Commit with a clear message

```
feat: add Kokoro voice model support for Korean

fix: resolve WebSocket disconnect on GPU memory pressure

docs: clarify networking setup for non-standard ports
```

### 6. Open a Pull Request

- Describe what changed and why
- Include screenshots for UI changes
- Mention any new dependencies
- Reference related issues if applicable

## Reporting bugs

Before filing an issue:

1. **Check existing issues** — someone might have already reported it
2. **Reproduce in a clean environment** — `docker compose down && docker compose up --build`
3. **Include your setup:**
   - Hardware (CPU, GPU, RAM)
   - Docker version
   - OS and version
   - Relevant logs

**Template:**

```
**Describe the bug**
A clear description of what happened.

**Expected behavior**
What you expected to see.

**Environment**
- OS: 
- Docker version: 
- GPU (if applicable): 
- RAM: 

**Logs**
Relevant log output (redact any sensitive info)
```

---

## Suggesting features

We're open to new ideas — especially ones that keep Shell:B running locally, offline, and under your control. Before filing a feature request:

1. Check existing issues and the roadmap
2. Consider whether it aligns with the project's core values (local-first, privacy-preserving, user-owned)
3. Be specific about the problem you're trying to solve, not just the solution you want

Features that add cloud dependencies or external service requirements will be evaluated carefully — we'd rather implement a local alternative than introduce a vendor lock-in.

---

## Code of conduct

- **Be kind.** We're all volunteers here.
- **Assume good faith.** Even when someone's PR is wrong, they probably tried their best.
- **No harassment, discrimination, or toxicity.** It doesn't matter how good your code is — you'll be removed.
- **Disagree with the license?** You're welcome to fork and do whatever you want. But don't try to shame people for choosing it.
